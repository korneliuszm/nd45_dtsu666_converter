# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A **temporary Modbus protocol bridge**: one or more independent **bridges**, each polling an upstream device over **Modbus TCP** (as client) and re-serving it as a CHINT **DTSU666** power meter (as server), so a **Sigenergy** battery system can read it as its "Power Sensor". The output transport is config-selectable per bridge: **Modbus RTU / RS-485** or **Modbus TCP**. It is a bridging solution meant to run for a few months until a physical DTSU666 meter arrives — favor short, safe, working changes over long-term architecture.

This deployment runs **two bridges as two systemd services** (`nd45-dtsu666@nd45`, `nd45-dtsu666@etango`): `nd45` (Lumel ND45 → `/dev/ttyAMA2`, grid-tie balance) and the second bridge on `/dev/ttyAMA4` (PV farm production). See `docs/superpowers/specs/2026-07-30-huawei-smartlogger-source-design.md`.

**The second bridge's source is a config choice between two alternatives, and both ship in `config.json`.** `smartlogger` (Huawei SmartLogger, one TCP host) and `etango` (four CHINT e2TANGO relays, averaged/summed) are both wired to `/dev/ttyAMA4` and `metrics_port` 8082, with **exactly one `enabled`** — currently `etango`. This works because the collision validators iterate `bridge_specs` (enabled bridges only), so the idle alternative may legally keep the same port, and switching sources is a two-flag edit; enabling both at once is rejected at load with "both serve RTU on /dev/ttyAMA4". Switching also means swapping the systemd instance (`disable --now @smartlogger`, `enable --now @etango`) — a `run --bridge <name>` on a disabled bridge exits with "unknown bridge" and, with `StartLimitIntervalSec=0`, retries every 5s forever instead of failing visibly. See `docs/DEPLOY.md` §4.1.

It is **not** a 1:1 gateway: it translates between two different register maps via an intermediate canonical model in SI units.

## Commands

Development is on Windows (PowerShell + Git Bash); the deploy target is Ubuntu on a Seeed reComputer R1000. Use the project venv interpreter directly rather than activating:

- **Windows dev:** `.venv\Scripts\python.exe -m <tool>`
- **Linux target:** `.venv/bin/python -m <tool>`

```bash
python -m venv .venv && pip install -e ".[dev]"   # setup
python -m pytest -q                                # all tests
python -m pytest tests/test_codec.py::test_roundtrip_all_orders -v   # single test
python -m ruff check .                             # lint (line-length 100)
python -m nd45_dtsu666 run                         # run every enabled bridge
python -m nd45_dtsu666 --bridge etango run          # run ONE bridge (how systemd does it)
python -m nd45_dtsu666 monitor                     # bridges + a live dashboard panel each
python -m nd45_dtsu666 monitor_nd45                # all bridges run; show the ND45 one
python -m nd45_dtsu666 monitor_hsm                 # all bridges run; show the SmartLogger one
python -m nd45_dtsu666 monitor_etango              # all bridges run; show the eTango one
python -m nd45_dtsu666 rtudebug                     # run all, trace register reads on one
python -m nd45_dtsu666 diag                        # poll one bridge's source, print the table
python -m nd45_dtsu666 diag --interval 0.05        # ...at the bridge's own rate (see the aliasing note below)
python -m nd45_dtsu666 static                      # serve config/static_debug.values, no source connection
python -m nd45_dtsu666 selftest                    # serve synthetic DTSU data for mbpoll bench test
python -m nd45_dtsu666 --bridge etango diag        # single-bridge modes take --bridge
curl -s localhost:8081/metrics                     # Prometheus scrape (served by run/monitor/rtudebug/static)
```

**What `--bridge` means depends on the mode, and the split is not obvious.** `run`, `monitor*` and `rtudebug` go through `build_pipeline`, so **every** enabled bridge runs; there `--bridge` only picks which one is displayed or traced — except for `run`, where it also passes through `select_specs` and genuinely restricts the process to one bridge (how systemd starts it). `diag`, `selftest` and `static` never build a pipeline at all: they resolve a single bridge via `diagnostics.select_bridge` and touch nothing else, so nothing is polled or served on behalf of the siblings.

CI (`.github/workflows/ci.yml`) runs `ruff check` + `pytest` on Python 3.10/3.11/3.12. There is no separate build step — it's a pure Python package. 504 tests, ~6s.

## Architecture

Single-process **asyncio**, one event loop, no locks. The core data flow:

```
per bridge (the deployment runs one bridge per process; a process CAN hold several):

source (TCP slave) --FC03--> poller --decode--> CanonicalStore --> dtsu datastore
                                                     |             (encode -> DTSU registers)
                                        supervise_server (this bridge's freshness gate)
                                                     |
Sigenergy (RTU or TCP master) --FC03--> DTSU output server (serves instantly from the
                                        datastore, never waits on a source poll)
```

- `app.build_pipeline()` wires **every enabled bridge** and is shared by `run` (`run_app`), `monitor`, and `rtudebug`. It returns a `Pipeline` holding a list of `BridgeRuntime` (store, context, client, client_factory, heartbeat, stat holders — nothing shared between bridges) plus the coroutines and a `MetricsSource`. `Pipeline.store`/`.context`/`.client` are back-compat accessors for the **first** bridge, which is what the single-bridge modes use. When editing the wiring, change `build_pipeline`, not the callers.
- **Bridges are the unit of isolation, and that is load-bearing.** `config/config.json` lists *every* bridge under `bridges`, each entry the same `name`/`enabled`/`source`/`dtsu`/`safety`/`metrics_port` shape; only `prometheus` and `static_debug` sit outside it. Read `AppConfig.bridge_specs`, never the raw `nd45`/`dtsu`/`safety`/`primary_metrics_port` fields — those are the pre-multi-bridge layout, kept optional only so older config files still load, and `bridge_specs` assembles them into the first bridge. Each bridge has its **own** timings, and they differ by an order of magnitude — as deployed, ND45 polls every **0.05s** with `max_data_age_s` 3.0s, eTango every **0.2s** with 3.0s (it measures directly, so it can be fast despite 4 devices x 2 read blocks per cycle), and the disabled SmartLogger alternative every **1.0s** with 30.0s (it aggregates inverters over RS485 behind the TCP front end and cannot meet 3s). Config load rejects two bridges sharing a serial port — pymodbus 3.6.9's `listen()` swallows the `OSError`, so the loser would hang silently — and rejects `max_data_age_s < 2 x poll_interval_s`, which would park a bridge in permanent fail-safe. `slave_id` *may* repeat; the buses are electrically independent. `tests/test_bridge_isolation.py` is the file that guards all of this; `tests/test_config.py` covers the narrower per-side validators (overlapping register addresses within a `TargetSide`, `StaticIdentityPoint` ascii/uint32 shapes).
- **Two levels of isolation, both load-bearing.** *Inside* a process, bridges share nothing but the event loop. *Across* processes, `run --bridge <name>` (`app.select_specs`) restricts a process to one bridge, which is how systemd runs them — `systemd/nd45-dtsu666@.service`, `%i` = bridge name. That closes the last shared fate: a crash, OOM or `systemctl restart` on one service used to silence both meters. **Both services still load the whole `config.json` on purpose** — the validators that reject two bridges sharing a serial port only work when one configuration sees every bridge, and pymodbus swallows that bind error. Two processes cannot share a Prometheus port, hence `bridges[].metrics_port` and `AppConfig.metrics_port_for(only)`.
- **A hung poller is recovered in-process first, per bridge** (`app.supervise_poller`): no progress for `source.stall_timeout_s` means cancel the task, close the client, rebuild it via `client_factory`, reconnect, restart. The systemd watchdog is the backstop — `watchdog_loop` tracks poll-loop progress via `app.SlowestHeartbeat` (the least-progressing bridge in this process), and every `stall_timeout_s` (30s ND45, 60s SmartLogger) is deliberately below `WatchdogSec` (90s) so the cheap in-process rebuild always gets first crack. Escalating to a restart is safe now that each bridge is its own service. Important distinction: an *unreachable* source is not a stall — `run_poller` keeps cycling through its error path and touching the heartbeat, so nothing is rebuilt and only the freshness gate reacts.
- **The restart backstop only works because the unit disables systemd's start rate limiting** (`StartLimitIntervalSec=0`, `RestartSec=5`). With the defaults (`StartLimitBurst=5` per 10s) any crash-loop — or a transient like the RS-485 device not yet present after boot — trips the limit within ten seconds, systemd gives up *permanently*, and the instance sits in `failed` with the Power Sensor unserved until a human runs `systemctl reset-failed`. Hit for real 2026-08-04. Worst case now is one attempt every 5s forever: noisy, always self-recovering. **The directive must be in `[Unit]`, not `[Service]`** — systemd moved it in v229 and silently ignores it in the wrong section, so it looks like it worked until you check `systemctl show -p StartLimitIntervalUSec`.
- `codec.py` is a **`struct`-based** float32 ↔ register codec, plus a sized-integer half (`u16/i16/u32/i32/u64/i64`) used only by the Huawei source. Do **not** use pymodbus `BinaryPayloadBuilder`/`Decoder` (removed in newer pymodbus, and the version is pinned to `>=3.6,<3.7`). Huawei's documented "Gain" is a divisor but needs no new concept — it folds into the map's existing `scale` multiplier.
- `canonical.py` (`CanonicalStore`, `HealthGate`) holds the latest SI values + a timestamp and is the single source of truth. `dtsu_server.update_datastore` mirrors those values into the pymodbus datastore. It also holds `compute_derived` (canonical-model logic every source must run; re-exported from `nd45_poller` for existing importers) and `apply_derive`.
- **Huawei SmartLogger source** (`huawei_poller.py`). `poll_once` is signature-compatible with `nd45_poller.poll_once`, which is what lets `run_poller` drive either via `poll_once_fn`; `app._POLL_ONCE` is the only place a source type is dispatched on. It uses **sized integers** (Huawei's documented "Gain" is a divisor that folds into the map's existing `scale` multiplier) and **config-driven read blocks** (`SourceSide.read_groups`) rather than a module constant. Coverage is partial by necessity — no SmartLogger register set covers the full canonical model, and grid frequency appears **nowhere** in its manual — so the maps carry declarative `derive` rules (`canonical.apply_derive`). Two things to know: an invalid channel is zeroed rather than rejecting the whole sample (throwing away a whole slow aggregate poll over one disconnected inverter is too costly; a genuinely unreachable source still raises from `read_groups`), and it **does** call `compute_derived`, because its bridge owns a full canonical model and must fill `active_energy_total`/`net_*`. Point names are plain canonical names — the `bridge` metric label separates the two bridges, not a prefix.
- **CHINT e2TANGO source** (`etango_poller.py`), the alternative second-bridge source. Same `poll_once` contract as the other two, but it is the **only multi-host source**: `MultiHostClient` holds one `AsyncModbusTcpClient` per `EtangoDeviceConf` and presents the `connect()`/`close()`/`connected` interface `connect_with_retry`/`supervise_poller` expect, so those call sites stay source-agnostic (`app._make_client_factory` is where the branch lives). Four differences from the Huawei path, all deliberate: (1) reads are **FC=04** (`read_input_registers`), not FC=03; (2) each device is decoded and its `derive` rules applied **per device, before combining** — `hypot`/`pf_from_p_s` are non-linear, so deriving then summing is physically right and combining then deriving is not; (3) values are then **averaged or summed per canonical point**, declared in `registers.json` as `SourcePoint.aggregate`/`DeriveOp.aggregate` (`"avg"` for U/I/freq/PF, `"sum"` for P/Q/S/energies — S is summed from each relay's own S register, never recomputed from summed P/Q); (4) it is **strict** where Huawei is forgiving — any read error, short read, non-finite value, or a raw register at/above `codec.OVERRANGE` (1e20, checked before scaling — load-bearing since the energy points' `scale: 0.001` would otherwise shrink a sentinel under the threshold) on *any* device raises `PollError` for the whole sample, because a group of feeder meters silently losing one member would understate the total by an unflagged amount. Every configured device is read each cycle regardless of its `aggregate` flag, so a device that must not be able to fail the bridge has to be removed from `devices`, not just flagged `false`. Word order is **CDAB** (`word_order: little`, `byte_order: big`) per the manual's documented `B3,B4,B1,B2` layout — traced through `codec.registers_to_float` but not yet confirmed on live hardware. **Energy registers are Wh/varh on the wire but this project's canonical model is kWh/kvarh** (see `docs/register-map.md`); `imp_energy_total`/`exp_energy_total`/`reactive_imp_energy_total`/`reactive_exp_energy_total` therefore carry `scale: 0.001`, unlike every other etango point (all `1.0`, vendor unit already matches canonical) — found by a live audit 2026-08-07 after shipping with `scale` omitted (defaulting to `1.0`) reported energy 1000x too large, silently (it still encodes as a valid float32, nothing raises). Guarded by `tests/test_etango_poller.py::test_documented_units_agree_with_the_scales_in_the_map` (`ETANGO_DOC`), the etango equivalent of `test_docs.py`'s Huawei gain check — add every new point to `ETANGO_DOC` too, or the guard cannot see it. **Averaging `pf_total`/`pf_l1..3` across independent feeders is a known approximation**: the physically correct aggregate power factor is `sum(P)/sum(S)`, not the mean of each device's own PF, and the two diverge under unbalanced loading across the four relays (e.g. a heavily-loaded high-PF feeder averaged with a lightly-loaded low-PF one skews toward the mean instead of the P/S-weighted truth). Fixing this would need a "derive after combination" hook the architecture does not have (`apply_derive` runs per-device before `_combine`); acceptable for now on a PV farm where the four feeders carry comparable load, but verify at bring-up if that assumption is wrong for a given site. Also unverified: whether the four relays report **primary-side** values, which `dtsu_target`'s `divide_by_ct` assumes (see `dtsu_server.encode_target_point`'s docstring) — low-stakes in practice since Sigenergy only reads the `fc=4` map, where `divide_by_ct` is `false` throughout.
- **Fail-safe** (`dtsu_server.supervise_server`): one instance **per bridge**. When a bridge's data is older than *its own* `safety.max_data_age_s`, *that* bridge's output server is **stopped** (goes silent) so the Sigenergy on that bus detects a timeout and enters its own safe mode; it restarts automatically when data returns. A sibling bridge is unaffected — verified live in both directions.
- **Watchdog** (`watchdog.py`): the systemd unit's `WatchdogSec=` (read from the `WATCHDOG_USEC` env var, no duplication in `config.json`) drives a heartbeat fed by poll-loop progress, aggregated through `app.SlowestHeartbeat`. See `docs/superpowers/specs/2026-07-06-systemd-watchdog-design.md` for the original design and `2026-07-30-huawei-smartlogger-source-design.md` for the ordering against in-process stall recovery.
- **Metrics** (`metrics.py`): a read-only Prometheus endpoint on `asyncio.start_server` (no `prometheus_client` -- its `start_http_server` uses a thread, and this process is one loop with no locks). It reads existing state at scrape time (`CanonicalStore`, `RtuActivity`, `Heartbeat`) plus two new holders, `PollStats` (fed by `build_pipeline`'s `on_update`/`on_error`; the poller is untouched) and `ServerStatus` (set by `supervise_server`'s optional `status=`, since server state is otherwise loop-local and cannot be re-derived from the freshness gate). Two things are easy to get wrong: the task is created **before** `connect_with_retry` in every runner -- `pipe.coros` only start after the ND45 connects, and an endpoint that is down during an ND45 outage is useless -- and `build_pipeline` now creates an `RtuActivity` itself when the endpoint is enabled, so `run` gets read stats too. See `docs/superpowers/specs/2026-07-27-prometheus-metrics-design.md`.
- `monitor.py` renders **one screen per bridge** from a pure `render_bridge_monitor(BridgeSnapshot)`: upstream link state + decoded values (SOURCE), and server state + Sigenergy read activity **on that bridge's own port** (OUTPUT). The served-register dump was removed on purpose — it pushed the link and activity lines off screen, and `rtudebug` already traces register blocks. `monitor_nd45`/`monitor_hsm` resolve a bridge by *source type* (`select_bridge_by_source`), so a renamed bridge still works; every bridge runs regardless of which one is displayed. Two counters, not one, and the distinction is the whole point: `RecordingSlaveContext` sees only requests that *reach the datastore*, while `WireActivity` (fed by `dtsu_server.tracing_rtu_framer`, an `ModbusRtuFramer` subclass wrapping `processIncomingPacket`) counts raw bytes and CRC-valid frames *before* pymodbus filters by slave id — a frame for a foreign slave is dropped by the framer with only a DEBUG log, so without the bus counter "Sigenergy reads: 0" cannot be told apart from "polled under the wrong address". RTU only; a TCP output has no shared wire. Read requests from Sigenergy (over either transport) are captured via `RecordingSlaveContext` (a `ModbusSlaveContext` subclass logging every `getValues` into an `RtuActivity` tracker); passing `activity=` to `build_pipeline` now gives **every** bridge its own recorder, not just the first — otherwise a sibling panel could not answer "is Sigenergy polling this port?" with the metrics endpoint switched off.

## Register maps and translation (the crux)

- The maps live in **`config/registers.json`** (seeded from the device PDFs) and are edited **without touching code**. ND45 addresses are **decimal**; DTSU666 addresses are **decimal converted from the manual's hex**. `config/config.json` holds runtime params per bridge (source IP/unit/intervals, output transport + its params, slave id, `max_data_age_s`).
- **Source sections vs output maps.** `registers.json` holds one source section per device kind (`nd45_source`, `huawei_plant_source`, `huawei_meter_source`, `etango_source`), selected by a bridge's `source.register_map`; the four output maps (`dtsu_target`, `dtsu_sigen_ext_target`, `dtsu_sigen_ext_energy`, `dtsu_sigen_identity`) are **shared by every bridge** — they all emulate the same meter. What differentiates a bridge's output is only its `dtsu.identity.ir_at`, passed to `update_datastore` as the runtime `ct_ratio`. Read them via `RegisterMap.targets` / `RegisterMap.source_by_name`.
- **The CT split across the two output maps is copied from the real Sigen meter and is confirmed correct — do not "fix" it.** Points in the classic `dtsu_target` (fc=3) carry `divide_by_ct: true` and are divided by `dtsu.identity.ir_at` in `encode_target_point`; the Sigen OEM map `dtsu_sigen_ext_target` (fc=4) is **not** divided, because it is the primary-side map. Measured on the live system 2026-08-04: Sigenergy regulates exclusively on **fc=4, addr=5404, count=16** (`dtsu_sigen_ext_target`, `p_total`..`q_l3`, ~9.5 reads/s) and never reads `dtsu_target` at all — worth knowing when changing maps, but not a fault. A theory that Sigenergy double-applies its CT ratio to the ext map was checked against the app's own displayed values and is **wrong; it has been closed.**
- **Transform semantics** (implemented in `codec.decode_point`/`encode_point`, must stay exact):
  - ND45 → canonical: `SI = (raw_float * scale * sign) + offset`
  - canonical → DTSU register: `register_float = (SI * sign * scale) + offset`
  - DTSU scales are e.g. V×10, A×1000, W×10, PF×1000, Hz×100; energy is direct kWh. `sign ∈ {+1,-1}` flips import/export.
- Both sides default to big/big (ABCD) word/byte order, configurable per side.
- **Site MV/LV scaling:** this installation's ND45 measures at the medium-voltage side (~9kV phase / 15588V line) via the site's step-down transformer, not at the 230V/400V point where a physical DTSU666/Sigen Sensor is normally mounted. `nd45_source` therefore carries a non-1.0 `scale` on `u_l1/l2/l3/l12/l23/l31` (÷37.5, the nameplate MV/LV ratio) and `i_l1/l2/l3` (×37.5) so canonical voltage/current already represent the equivalent LV-side reading before any DTSU encoding. Power/energy points are left unscaled since `P = U·I` is conserved across an (assumed-ideal) transformer — do not also scale `p_*`/`q_*`/`s_*`. If the transformer ratio is confirmed on-site to differ from 37.5, update only these six `scale` values.

## Things that only make sense across files

- **The ND45 over-range check runs on the raw register value, not the scaled one** (`nd45_poller.poll_once`). `codec.OVERRANGE` (1e20) describes the meter's own out-of-range sentinel (2e20), so a map `scale` below 1 would shrink the sentinel under the threshold — with the MV/LV voltage scale of 1/37.5 it lands at 5.3e18 and used to be served as a real voltage. Anything that changes those `scale` values must leave the check on `raw`. Nothing else in the chain can alter a sign or overflow: everything on the wire is float32 with ~13 orders of magnitude of headroom over this site, and `tests/test_codec.py` pins sign preservation end to end so a field-observed sign swing is the source's, not the bridge's.
- **The ND45 poll interval is 0.05s because the meter itself refreshes at ~7.5 Hz.** Measured 2026-08-04: `p_total` changes about every 134 ms (median over 114 observed changes at 837 reads/s). The earlier 0.2s meant the bridge sampled *slower than the source moved* and aliased it, on top of holding each value up to 200 ms — a defect on its own terms. The useful negative result: sign changes per minute were unchanged within noise (41 at 0.2s vs 41 and 45 at 0.1s over 60s each; the config then went to 0.05s for margin), so **this did not fix the limit cycle below** — the bridge's share of the loop's dead time is too small to matter, and the dominant lag is in Sigenergy's regulation or the plant. CPU is ~5% either way and the link sustains 837 reads/s at 0.8 ms round-trip, so the fast rate is effectively free. Don't "optimize" it back up.
- **`diag` and `monitor` sample at different rates, and that alone explains most "they disagree" reports.** `diag` polls at its own `--interval` (1s default), the ND45 bridge at `source.poll_interval_s` (0.05s) — a 20x gap; both redraw once a second, so the screens invite a comparison that is not like-for-like. Sampling slower aliases a swing away rather than removing it, so the slower screen looks calmer for a signal that is genuinely moving. `canonical.SampleStats` (rolling, fed by `on_update` into `BridgeRuntime.spread`; session-length in `diag`) is what makes the two comparable — same statistic on both screens. The decode path is identical: verified against a constant-image fake meter, where the whole monitor pipeline reports frozen values across 41 polls.
- **The real cause of "diag steady, service/monitor swinging" is the plant, not the bridge (2026-08-04).** `p_total` swinging rail-to-rail within seconds, no read or decode error, not self-correcting, is a **closed-loop limit cycle**: Sigenergy regulates against the meter this bridge serves, its response comes back through the grid connection, and the loop hunts with a ~3.1–3.3s period. Confirmed three ways on live hardware: (a) a second, fully independent reader (own process, own TCP client, no output server — i.e. exactly what `diag` does) saw the identical swing **sample for sample** while the service ran; (b) `u_l1` and `freq` stayed flat throughout (0.5V / 0.02Hz peak-to-peak) while `i_l1` moved 125→484A, which no decode fault produces; (c) stopping this bridge collapsed the swing to **zero sign changes** within ~2s and restarting it brought the cycle straight back, unchanged. **`diag` looks steady only because it is normally run with the service stopped** (`README.md` says to) — Sigenergy then loses the sensor, enters its own safe mode and stops regulating. That is not a like-for-like comparison of two decoders; it is a comparison of a regulating plant against an idle one. Before blaming this code for an unstable reading, reproduce it with a second reader **while the service keeps running**.
- **Two earlier "corruption" findings from the same day were this limit cycle, misattributed, and have been retracted.** Both blamed the bridge for the swing and were confounded the same way — every arm of each A/B changed whether (or how steadily) Sigenergy was being fed, so each measured the plant's reaction, not a decode fault: (1) `RtuActivity`/`RecordingSlaveContext` corrupting the concurrent source poll — it does not, and `build_bridge` auto-creates the recorder for `run` again, gated on `config.prometheus.enabled`; (2) "two bridges in one process corrupt the ND45 reading" (`docs/DEPLOY.md` §0.1) — one bridge per systemd service is still right for **fault isolation**, which is its own good reason, but not because a sibling bridge corrupts data. No pymodbus 3.6.9 bug is implicated in either.
- **The active-power sign convention is confirmed correct as `sign: +1` (2026-08-04, measured).** Tested by flipping `p_total`/`p_l1..l3` to `-1` in both output maps on the live system. Unregulated (bridge stopped) the site sits at **+230 kW**; with `+1` the loop pulls the mean down to **+71 kW** — right direction, but unstable; with `-1` it ran the grid *up* to **+789 kW** and pinned there, dead steady (8.6 kW peak-to-peak). That flat line is **saturation, not stability**: the controller pushes in the direction that increases the error until it hits its power limit. A stable-looking number here is the worse outcome, so do not read "no oscillation" as "fixed". The remaining instability at `+1` is therefore a **loop gain/timing** problem, not a sign problem.
- **The limit cycle is still open, and three of its suspects are now eliminated** (`docs/DEPLOY.md` §0.2). Magnitude, sign and CT scaling are each confirmed correct, and halving the poll interval changed the sign-change rate not at all. What is left is the timing/tuning side — Sigenergy's own regulation period and dead band, plus whatever phase lag this bridge adds over a directly-wired DTSU666 (RTU serving latency at 9600 baud is now the larger half of that budget, not the poll). Not yet investigated. Treat a new instability report as a continuation of this, not a fresh bug, until a second independent reader says otherwise.
- **Two clocks in `monitor`/`poller`/`metrics` are intentional:** data-age uses the asyncio loop clock (`loop.time()`, what the poller stamps into the store); output-request timing uses `time.monotonic()` (what `RecordingSlaveContext` stamps). Keep each metric on its own clock -- `metrics.render()` takes both clocks as arguments and never calls one itself.
- **Tests never open a real serial port or TCP socket.** The poller is tested with a fake duck-typed client; the DTSU output server (either transport) is tested at the datastore level (`getValues`/`setValues`) and the supervisor with an injected `server_factory` + fake clock. Real RS-485, real TCP sockets, and live Sigenergy behavior are out of scope for the suite. The metrics endpoint follows this too: its HTTP layer is covered through the pure `parse_request`/`route`/`_response` functions, never a real listener.
- **Deployment is symlink-swap, and on the live host `/etc` is a RAM overlay** (`docs/DEPLOY.md` §1 and §0.4). The units point at `/persistence/app/current_modbus_converter`, a symlink to whichever checkout is live, so an upgrade is "check out beside the old one, repoint the symlink, restart both instances" and the unit files never change. The trap: this host mounts `/` as an overlayroot whose writable layer is **tmpfs**, so `systemctl enable`, unit files copied into `/etc/systemd/system/`, and `systemctl disable` of an old unit all **evaporate on reboot**. Found for real 2026-08-04, hours after cutover, with the live units existing only in RAM while the disk still had July's retired single-process unit enabled. `/persistence` is a real partition, so the checkout and config are safe — only systemd state is at risk. Write through `overlayroot-chroot` (where `/persistence` is *not* mounted, so feed unit contents in by heredoc) and verify all three copies with `md5sum`.

## Reference

- **`docs/DEPLOY.md`** — the install/upgrade/rollback procedure, this site's known-good reference config, and a §0 of field incidents worth reading *before* touching the service. It ships in the checkout on purpose (a second device needs the procedure, not just the code). `README.md` covers day-to-day operation and the on-site verification checklist.
- **Register maps** — `docs/register-map.md` (ND45 bridge) and `docs/smartlogger-dtsu-map.md` (SmartLogger bridge; tables generated from `config/registers.json` by `scripts/gen_smartlogger_map_doc.py` — re-run it after editing the `huawei_*` sections or `tests/test_docs.py` fails).
- **`scripts/`** — standalone hardware diagnostics, not part of the package and not covered by the suite. `poll_physical_dtsu666.py` and `full_scan_dtsu666.py` talk to a **real** DTSU666 over RTU (used to verify sign/scaling independently of this code); `query_bridge_tcp.py` reads the bridge's own output server over TCP without touching RS-485.
- **Design and plan docs** live in `docs/superpowers/specs/` and `docs/superpowers/plans/`. The device manuals are PDFs in the repo root (not indexed by glob — use `Get-ChildItem -Recurse -Force`); extract text with `pdfplumber` (poppler is unavailable in this environment).
